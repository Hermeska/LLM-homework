# Исследование оптимизаций обучения Qwen3

## Цель работы

Цель эксперимента — увеличить количество **полезных токенов в секунду** при
обучении модели, не изменяя модель, данные и обязательные гиперпараметры.
Главная метрика:

```text
tokens_per_second = число полезных target-токенов / измеренное время
S = final tokens_per_second / baseline tokens_per_second
```

Полезными считаются токены, участвующие в вычислении loss; padding-токены не
учитываются. Первые 10 шагов исключаются из измерения производительности как
разогрев.

Запуск в Aviflow: [qwen3-training-optimizations-v2](https://aviflow.k.avito.ru/_/pipeline/?ns=students#/runs/details/9474ce12-f59f-4ba4-bab4-5f307c824be7)

Статус pipeline: **SUCCEEDED**. Все эксперименты выполнялись последовательно
внутри одного GPU-компонента на `NVIDIA A100 80GB PCIe` (`torch 2.14.1+cu130`).

## Зафиксированные условия

Во всех запусках сохранены требования исходного шаблона:

- модель Qwen3 создаётся с нуля;
- токенизатор, датасет и разделение train/validation не меняются;
- максимальная длина последовательности — 512;
- эффективный batch size — 64;
- обучение в BF16, TF32 включён;
- оптимизатор — `adamw_torch_fused`;
- learning rate — `3e-4`;
- scheduler — `constant_with_warmup`, `warmup_steps=200`;
- `seed=42`, `data_seed=42`;
- attention implementation — PyTorch SDPA;
- одинаковые evaluation и подсчёт метрик.

Каждый профиль запускался в отдельном Python-процессе. После завершения процесса
его модель и CUDA-контекст освобождались, а следующая модель создавалась с нуля.
Baseline и итоговый профиль обучались по 300 секунд на той же самой GPU. Проверка
лимита выполняется между optimizer steps, поэтому фактическое время может быть
немного больше 300 секунд.

## Проверенные конфигурации

| Профиль | Изменение относительно baseline | Назначение |
|---|---|---|
| `baseline` | batch 32 × accumulation 2 | Исходная точка сравнения |
| `batch-64` | batch 64 × accumulation 1 | Проверка более крупного microbatch |
| `checkpointing` | activation checkpointing | Снижение памяти ценой повторных вычислений |
| `packing` | wrapped sequence packing | Уменьшение вычислений над padding |
| `compile` | `torch_compile=True` | Компиляция вычислительного графа |
| `liger` | Liger kernels | Fused kernels и снижение расхода памяти |
| `activation-offload` | перенос активаций на CPU | Минимизация GPU memory |
| `packing-compile` | packing + compile | Сочетание двух оптимизаций |
| `packing-liger` | packing + Liger | Второе сочетание оптимизаций |

Короткие подборочные запуски имели лимит 60 секунд. Лучший профиль после этого
повторно запускался с нуля на 300 секунд.

## Наблюдения

### 1. Packing дал основной прирост скорости

Одиночный `packing` достиг 21 936.66 tokens/s — примерно в 3.21 раза больше
baseline. В baseline короткие документы дополняются padding до длины самого
длинного документа в batch, поэтому GPU выполняет вычисления над позициями,
которые не участвуют в loss. Packing объединяет тексты в плотные блоки длиной
512 и резко повышает долю полезных токенов.

При этом у packing меньше optimizer steps, но намного больше полезных токенов на
каждом шаге. Поэтому число шагов само по себе не является показателем скорости.

### 2. Packing и `torch.compile` хорошо работают вместе

Комбинация `packing-compile` достигла 32 567.86 tokens/s против 21 936.66 у
одиночного packing — дополнительное ускорение **1.48×**. Packing делает формы
batch более регулярными, а это удобно для повторного использования
скомпилированного графа. Именно этот профиль был выбран для финального запуска.

Отдельный короткий запуск `compile` не дал корректной оценки throughput:
компиляция первого шага заняла дольше установленного лимита, был выполнен только
один optimizer step, а измерение начинается после 10 warmup steps. Это показывает,
что compile нужно оценивать на достаточно длинном запуске или вместе с нагрузкой,
которая окупает стартовую стоимость компиляции.

### 3. Экономия памяти имеет цену по скорости

Activation checkpointing уменьшил peak memory с 41.24 до 17.39 GiB, то есть
примерно на 57.8%, но скорость снизилась с 6 824.94 до 5 643.13 tokens/s
(`−17.3%`). Причина — часть активаций не хранится, а повторно вычисляется во время
backward pass.

Activation offloading показал ещё меньший peak — 13.36 GiB (`−67.6%` относительно
baseline), но из-за обмена данными между CPU и GPU успел выполнить только два
шага. После исключения warmup шагов данных для `tokens_per_second` не осталось.
Эта оптимизация полезна при дефиците GPU memory, но не для максимальной скорости
на A100 80GB.

### 4. Увеличить microbatch до 64 без memory-оптимизаций нельзя

Профиль `batch-64` сохранил effective batch size 64, заменив схему `32 × 2` на
`64 × 1`, но завершился CUDA OOM. В момент ошибки процессу потребовалось ещё
6.14 GiB, когда свободно было около 4.98 GiB. Следовательно, gradient
accumulation в baseline необходим, чтобы effective batch 64 помещался в память.

### 5. Liger снизил память, но один не ускорил эту нагрузку

Одиночный Liger использовал 26.83 GiB вместо 41.24 GiB (`−34.9%`), но показал
6 235.93 tokens/s — примерно на 8.6% медленнее baseline. В сочетании с packing
скорость выросла до 26 180.52 tokens/s: это в 1.19 раза быстрее packing без
Liger, однако всё ещё медленнее комбинации packing + compile. Следовательно,
результат сочетания оптимизаций нельзя предсказать простым сложением их отдельных
эффектов — его нужно измерять.

## Вывод

Лучшей конфигурацией стала `packing-compile`: wrapped sequence packing,
`torch_compile=True`, batch 32 и gradient accumulation 2. Она сохранила все
обязательные параметры задания и на той же A100 увеличила полезную пропускную
способность с 6 824.94 до 32 575.36 tokens/s. Итоговое ускорение составило
**4.773×**, peak GPU memory уменьшился на **28.2%**, а validation loss после
одинаковых пяти минут обучения снизился с **6.6859 до 5.9023**.
